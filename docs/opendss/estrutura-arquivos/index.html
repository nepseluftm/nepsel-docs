Estrutura de Arquivos

Finalidade da Organização dos Arquivos​

A separação dos componentes do circuito em diferentes arquivos possui os seguintes objetivos:

  • facilitar a localização dos elementos;
  • reduzir a extensão do arquivo principal;
  • evitar repetição de comandos;
  • permitir a reutilização de modelos;
  • simplificar alterações;
  • facilitar a identificação de erros;
  • melhorar a rastreabilidade dos parâmetros;
  • permitir a criação de diferentes cenários;
  • favorecer o trabalho colaborativo;
  • facilitar o controle de versões;
  • organizar os dados de entrada e saída;
  • melhorar a reprodutibilidade dos estudos.

Em projetos com muitos elementos, a utilização de um único arquivo pode dificultar a manutenção e aumentar a probabilidade de erros. Por esse motivo, recomenda-se dividir o modelo em blocos funcionais.

Arquivo Principal Master.dss​

O arquivo Master.dss funciona como ponto de entrada da simulação. Ele deve organizar a sequência de carregamento dos demais arquivos, definir as bases de tensão, configurar o modo de solução e executar os comandos necessários.

Um exemplo de estrutura é apresentado a seguir:

Clear

Set DefaultBaseFrequency=60

Redirect Circuito.dss
Redirect LineCodes.dss
Redirect Linhas.dss
Redirect Transformadores.dss
Redirect Cargas.dss
Redirect Curvas/CurvasCarga.dss
Redirect Geracao.dss
Redirect Armazenamento.dss
Redirect Controles.dss
Redirect Medidores.dss

Set VoltageBases=[13.8, 0.38, 0.22]
CalcVoltageBases

Set Mode=Snapshot
Set ControlMode=Static

Solve

O arquivo principal deve conter apenas os comandos necessários para organizar e executar o modelo. Sempre que possível, os parâmetros específicos dos elementos devem ser mantidos em arquivos separados.

Ordem de Carregamento​

A ordem de execução dos arquivos deve respeitar as dependências existentes entre os elementos.

Uma sequência recomendada é:

  1. limpar o ambiente;
  2. configurar a frequência;
  3. criar o circuito principal;
  4. criar os códigos de linha;
  5. criar as linhas;
  6. criar os transformadores;
  7. criar as cargas;
  8. criar as curvas temporais;
  9. inserir a geração distribuída;
  10. inserir os sistemas de armazenamento;
  11. criar os controles;
  12. criar os medidores e monitores;
  13. definir as bases de tensão;
  14. configurar o modo de solução;
  15. executar a simulação;
  16. exportar os resultados.

Um elemento não deve ser chamado antes da criação dos objetos dos quais depende.

Por exemplo, uma linha que utiliza determinado LineCode deve ser criada somente após a definição desse código.

Arquivo Circuito.dss​

O arquivo Circuito.dss deve conter a definição do circuito principal e da fonte equivalente.

Exemplo:

New Circuit.MicrorredeUFTM
~ BasekV=13.8
~ pu=1.0
~ Phases=3
~ Bus1=Subestacao
~ Frequency=60
~ Angle=0

Esse arquivo também pode incluir os parâmetros equivalentes da rede, quando disponíveis.

Exemplo:

New Circuit.MicrorredeUFTM
~ BasekV=13.8
~ pu=1.0
~ Phases=3
~ Bus1=Subestacao
~ Frequency=60
~ MVAsc3=250
~ MVAsc1=180

Os parâmetros da fonte devem ser definidos com base nos dados reais ou nas hipóteses adotadas no estudo.

Arquivo LineCodes.dss​

O arquivo LineCodes.dss reúne os modelos de condutores utilizados no projeto.

Exemplo:

New LineCode.CaboMT_01
~ NPhases=3
~ R1=0.320
~ X1=0.290
~ R0=0.750
~ X0=0.680
~ C1=3.4
~ C0=1.6
~ Units=km

Outro exemplo:

New LineCode.CaboBT_01
~ NPhases=3
~ R1=0.641
~ X1=0.083
~ R0=1.920
~ X0=0.250
~ Units=km

A utilização de códigos de linha evita a repetição dos parâmetros em cada trecho e facilita alterações futuras.

Arquivo Linhas.dss​

O arquivo Linhas.dss deve conter os trechos de rede que interligam as barras do sistema.

Exemplo:

New Line.Linha_MT_01
~ Bus1=Subestacao.1.2.3
~ Bus2=Primario_TR01.1.2.3
~ Phases=3
~ LineCode=CaboMT_01
~ Length=0.150
~ Units=km

Exemplo para baixa tensão:

New Line.Linha_BT_01
~ Bus1=Secundario_TR01.1.2.3.0
~ Bus2=QDG.1.2.3.0
~ Phases=3
~ LineCode=CaboBT_01
~ Length=0.080
~ Units=km

Cada linha deve possuir um nome único e descritivo.

Arquivo Transformadores.dss​

O arquivo Transformadores.dss deve reunir os transformadores do sistema.

Exemplo:

New Transformer.TR01
~ Phases=3
~ Windings=2
~ XHL=5.5
~ kVA=300

~ Wdg=1
~ Bus=Primario_TR01.1.2.3
~ Conn=delta
~ kV=13.8
~ kVA=300
~ %R=0.5

~ Wdg=2
~ Bus=Secundario_TR01.1.2.3.0
~ Conn=wye
~ kV=0.38
~ kVA=300
~ %R=0.5

Também podem ser incluídos parâmetros relacionados às perdas em vazio e à corrente de magnetização:

~ %NoLoadLoss=0.3
~ %IMag=0.5

Os valores devem ser obtidos em dados de placa, relatórios de ensaio ou documentação técnica.

Arquivo Cargas.dss​

O arquivo Cargas.dss deve conter todas as cargas do circuito.

Exemplo de carga trifásica:

New Load.Carga_QDG
~ Bus1=QDG.1.2.3.0
~ Phases=3
~ Conn=wye
~ kV=0.38
~ kW=25
~ PF=0.92
~ Model=1
~ Daily=Curva_Carga_Geral

Exemplo de carga monofásica:

New Load.Carga_Fase_A
~ Bus1=QDG.1.0
~ Phases=1
~ Conn=wye
~ kV=0.22
~ kW=3.5
~ PF=0.95
~ Model=1

Exemplo de carga bifásica:

New Load.Carga_Bifasica
~ Bus1=QDG.2.3
~ Phases=1
~ Conn=delta
~ kV=0.38
~ kW=7.0
~ PF=0.94
~ Model=1

As cargas devem ser identificadas de forma coerente com os circuitos e equipamentos representados.

Arquivos de Curvas Temporais​

As curvas temporais devem ser organizadas em uma pasta específica, especialmente em estudos diários ou anuais.

Curva Inserida Diretamente​

Exemplo:

New LoadShape.Curva_Carga_Geral
~ Npts=24
~ Interval=1
~ Mult=(0.40 0.38 0.35 0.34 0.36 0.45
~       0.58 0.72 0.85 0.92 0.98 1.00
~       0.97 0.95 0.92 0.90 0.94 1.00
~       0.98 0.88 0.76 0.65 0.55 0.47)

Curva Importada de Arquivo CSV​

Exemplo:

New LoadShape.Curva_Carga_Geral
~ Npts=96
~ MinInterval=15
~ Mult=(file=Curvas/arquivos_csv/curva_carga.csv)

A utilização de arquivos CSV é recomendada quando a curva possui muitos pontos.

Arquivo Geracao.dss​

O arquivo Geracao.dss deve reunir os recursos de geração distribuída, como sistemas fotovoltaicos e geradores.

Exemplo de sistema fotovoltaico:

New PVSystem.FV_Microrrede
~ Bus1=QDG.1.2.3
~ Phases=3
~ Conn=wye
~ kV=0.38
~ kVA=20
~ Pmpp=19.98
~ PF=1.0
~ Irradiance=1.0
~ Daily=Curva_Irradiancia
~ TDaily=Curva_Temperatura

Curva de irradiância:

New LoadShape.Curva_Irradiancia
~ Npts=24
~ Interval=1
~ Mult=(0 0 0 0 0 0.05
~       0.18 0.38 0.60 0.78 0.90 0.98
~       1.00 0.96 0.85 0.68 0.45 0.22
~       0.08 0 0 0 0 0)

Os parâmetros devem representar as condições reais ou o cenário de estudo adotado.

Arquivo Armazenamento.dss​

O arquivo Armazenamento.dss deve conter os elementos relacionados ao banco de baterias.

Exemplo:

New Storage.BESS_Microrrede
~ Bus1=QDG.1.2.3
~ Phases=3
~ Conn=wye
~ kV=0.38
~ kWRated=12
~ kWhRated=15
~ %Stored=80
~ %Reserve=20
~ %EffCharge=95
~ %EffDischarge=95
~ State=IDLING

O estado do armazenamento pode ser alterado conforme o cenário:

Edit Storage.BESS_Microrrede State=CHARGING
Edit Storage.BESS_Microrrede State=DISCHARGING
Edit Storage.BESS_Microrrede State=IDLING

Estratégias mais avançadas podem utilizar StorageController.

Arquivo Controles.dss​

O arquivo Controles.dss reúne os elementos responsáveis por controlar outros dispositivos.

Exemplos de classes de controle:

  • RegControl;
  • CapControl;
  • InvControl;
  • StorageController;
  • Relay;
  • Recloser;
  • Fuse.

Exemplo de controle do armazenamento:

New StorageController.Controle_BESS
~ Element=Line.Linha_BT_01
~ Terminal=2
~ MonPhase=AVG
~ ModeDischarge=PeakShave
~ kWTarget=20
~ ModeCharge=Time
~ TimeChargeTrigger=10

Os parâmetros devem ser definidos de acordo com a estratégia operacional estudada.

Arquivo Medidores.dss​

O arquivo Medidores.dss deve conter monitores, sensores e medidores de energia.

Exemplo de monitor:

New Monitor.Monitor_QDG
~ Element=Line.Linha_BT_01
~ Terminal=2
~ Mode=1
~ PPolar=No

Exemplo de medidor de energia:

New EnergyMeter.Medidor_Geral
~ Element=Line.Linha_BT_01
~ Terminal=1

Exemplo de monitoramento do sistema fotovoltaico:

New Monitor.Monitor_FV
~ Element=PVSystem.FV_Microrrede
~ Terminal=1
~ Mode=1
~ PPolar=No

A definição dos monitores deve considerar as grandezas necessárias para cada análise.

Arquivos de Cenários​

A pasta Cenarios pode ser utilizada para representar diferentes condições operacionais sem alterar permanentemente o modelo principal.

Cenário Base​

Edit PVSystem.FV_Microrrede Enabled=No
Edit Storage.BESS_Microrrede Enabled=No

Cenário com Fotovoltaico​

Edit PVSystem.FV_Microrrede Enabled=Yes
Edit Storage.BESS_Microrrede Enabled=No

Cenário com Armazenamento​

Edit PVSystem.FV_Microrrede Enabled=Yes
Edit Storage.BESS_Microrrede Enabled=Yes
Edit Storage.BESS_Microrrede State=DISCHARGING

Cenário com Recarga Veicular​

Edit Load.Estacao_Recarga Enabled=Yes
Edit Load.Estacao_Recarga kW=12.2

O cenário selecionado pode ser chamado pelo arquivo principal:

Redirect Cenarios/CenarioFV.dss

Resultados das Simulações​

Os resultados devem ser armazenados em uma pasta separada dos arquivos de entrada.

Exemplo de definição do diretório:

Set DataPath="Resultados"

Exportações comuns:

Export Voltages
Export Currents
Export Powers
Export Losses
Export Meters
Export Monitors

Uma organização possível é:

Resultados/
├── Cenario_Base/
│   ├── tensoes.csv
│   ├── correntes.csv
│   ├── potencias.csv
│   └── perdas.csv
├── Cenario_FV/
├── Cenario_BESS/
└── Cenario_Recarga/

Não se recomenda salvar os resultados na mesma pasta dos arquivos principais, pois isso dificulta a identificação dos arquivos de entrada.

Uso dos Comandos Compile e Redirect​

Os comandos Compile e Redirect executam arquivos DSS, mas apresentam diferenças importantes.

Comando Compile​

O comando Compile executa o arquivo e altera o diretório de referência para a pasta onde ele está localizado.

Exemplo:

Compile "C:\Projetos_OpenDSS\Projeto_01\Master.dss"

Normalmente, ele é utilizado para iniciar a execução do arquivo principal.

Comando Redirect​

O comando Redirect executa outro arquivo sem ser utilizado como entrada principal do projeto.

Exemplo:

Redirect Linhas.dss

Uma prática recomendada é utilizar:

  • Compile para executar o Master.dss;
  • Redirect dentro do Master.dss para chamar os demais arquivos.

Caminhos Relativos​

Recomenda-se utilizar caminhos relativos sempre que possível.

Exemplo:

Redirect Curvas/CurvasCarga.dss

Em vez de:

Redirect "C:\Users\Usuario\Documentos\Projeto\Curvas\CurvasCarga.dss"

Os caminhos relativos facilitam:

  • transferência do projeto;
  • compartilhamento entre usuários;
  • utilização em outros computadores;
  • publicação em repositórios;
  • execução por scripts;
  • manutenção da estrutura.

Para que funcionem corretamente, a posição relativa dos arquivos deve ser preservada.

Padronização dos Nomes​

Os arquivos e elementos devem utilizar nomes claros e consistentes.

Exemplos recomendados:

Linha_QDG_EVSE
Carga_Laboratorio
PVSystem_Microrrede
Storage_BancoBaterias
Monitor_Inversor01

Evite nomes genéricos como:

elemento1
teste2
novo
linha_final_corrigida

Uma convenção adequada facilita a localização dos elementos e reduz erros durante a alteração dos parâmetros.

~ Conn=wye

A documentação interna reduz a dependência de informações externas.

Arquivo de Documentação​

Recomenda-se criar um arquivo README.md na pasta principal do projeto.

Esse arquivo pode apresentar:

  • título do projeto;
  • objetivo da simulação;
  • descrição do sistema;
  • estrutura de pastas;
  • versão do OpenDSS;
  • versão do Python;
  • instruções de execução;
  • parâmetros principais;
  • fontes dos dados;
  • cenários disponíveis;
  • responsáveis;
  • limitações conhecidas;
  • histórico de alterações.

Exemplo:

# Modelo OpenDSS da Microrrede UFTM

## Execução

Compile o arquivo:

`Master.dss`

## Cenários

- cenário base;
- cenário com geração fotovoltaica;
- cenário com armazenamento;
- cenário com estação de recarga.

## Versão

OpenDSS: versão utilizada no projeto.

Controle de Versão​

Projetos OpenDSS podem ser armazenados em repositórios Git.

Uma estrutura com arquivos de texto é adequada para controle de versão, pois permite:

  • comparar alterações;
  • identificar responsáveis;
  • recuperar versões anteriores;
  • criar ramificações;
  • revisar mudanças;
  • compartilhar o projeto;
  • registrar o desenvolvimento.

Arquivos temporários ou resultados muito grandes podem ser excluídos do repositório por meio de um arquivo .gitignore.

Exemplo:

Resultados/
*.csv
*.log
__pycache__/
.venv/

Caso determinados resultados sejam necessários para validação, eles podem ser armazenados em uma pasta específica de referência.

Separação entre Dados de Entrada e Resultados​

Os dados de entrada não devem ser misturados com os arquivos de resultados.

Dados de Entrada​

Incluem:

  • parâmetros de linhas;
  • dados de transformadores;
  • potências das cargas;
  • curvas de consumo;
  • curvas de irradiância;
  • dados de baterias;
  • configurações dos controles.

Resultados​

Incluem:

  • tensões;
  • correntes;
  • potências;
  • perdas;
  • energia;
  • carregamentos;
  • dados de monitores;
  • gráficos;
  • relatórios.

A separação reduz o risco de utilizar resultados antigos como se fossem dados de entrada.

Integração com Python​

A pasta Scripts pode conter as rotinas utilizadas para executar o OpenDSS e tratar os resultados.

Exemplo simplificado:

from pathlib import Path

import opendssdirect as dss

projeto = Path(__file__).resolve().parents[1]
master = projeto / "Master.dss"

if not master.exists():
    raise FileNotFoundError(
        f"Arquivo principal não encontrado: {master}"
    )

dss.Text.Command("Clear")
dss.Text.Command(f'Compile "{master}"')
dss.Text.Command("Solve")

if not dss.Solution.Converged():
    raise RuntimeError(
        "A solução do circuito não convergiu."
    )

print("Circuito:", dss.Circuit.Name())
print("Barras:", dss.Circuit.NumBuses())
print("Nós:", dss.Circuit.NumNodes())

A utilização do objeto Path reduz problemas relacionados aos caminhos dos arquivos.

Arquivo de Configuração​

Projetos automatizados podem utilizar um arquivo separado para configurações.

Exemplo em formato JSON:

{
  "projeto": "Microrrede UFTM",
  "arquivo_master": "Master.dss",
  "modo_simulacao": "Daily",
  "passo_minutos": 15,
  "numero_passos": 96,
  "pasta_resultados": "Resultados"
}

Esse arquivo permite alterar parâmetros sem modificar diretamente o código Python.

Em projetos desenvolvidos por diferentes integrantes, recomenda-se definir responsabilidades por arquivos.

Exemplo:

Antes de incorporar alterações, o modelo completo deve ser testado.

Validação Progressiva​

A estrutura modular permite validar o projeto progressivamente.

Uma sequência recomendada é:

  1. executar somente o circuito principal;
  2. adicionar as linhas;
  3. verificar a conectividade;
  4. adicionar os transformadores;
  5. conferir as bases de tensão;
  6. adicionar as cargas;
  7. verificar o balanço de potência;
  8. adicionar a geração;
  9. verificar o fluxo de potência;
  10. adicionar o armazenamento;
  11. adicionar os controles;
  12. adicionar os medidores;
  13. executar os cenários;
  14. comparar os resultados.

Essa abordagem facilita a localização de erros.

Verificação dos Arquivos​

Antes de executar o projeto, confira:

  • existência de todos os arquivos chamados;
  • nomes corretos;
  • extensões .dss;
  • caminhos relativos;
  • ausência de arquivos duplicados;
  • sequência correta dos comandos;
  • criação prévia dos objetos utilizados;
  • coerência entre as unidades;
  • nomes das barras;
  • nomes dos elementos;
  • bases de tensão;
  • frequência do sistema;
  • modo de solução.

Um erro em qualquer arquivo chamado pelo Master.dss pode impedir a compilação do projeto.

Erros Frequentes de Organização​

Entre os erros mais comuns, destacam-se:

  • arquivo Redirect inexistente;
  • caminho digitado incorretamente;
  • duplicação do nome de elementos;
  • alteração da estrutura de pastas;
  • utilização de caminhos absolutos;
  • mistura entre entrada e saída;
  • criação de elementos em ordem incorreta;
  • arquivos com extensão .dss.txt;
  • nomes com caracteres especiais;
  • diferentes versões do mesmo arquivo;
  • ausência de documentação;
  • resultados antigos mantidos na pasta principal.

Modelo de Master.dss Completo​

O exemplo abaixo apresenta uma estrutura mais completa:

! ============================================================
! MODELO OPENDSS — MICRORREDE EXPERIMENTAL ICTE/UFTM

! ============================================================

Clear

Set DefaultBaseFrequency=60

Redirect Circuito.dss
Redirect LineCodes.dss

Redirect Transformadores.dss

Redirect Curvas/CurvasGeracao.dss
Redirect Cargas.dss
Redirect Geracao.dss
Redirect Armazenamento.dss
Redirect Controles.dss
Redirect Medidores.dss

Redirect Cenarios/CenarioBase.dss

Set VoltageBases=[13.8, 0.38, 0.22]
CalcVoltageBases

Set MaxControlIterations=100

Show Summary
Show Voltages LN Nodes
Show Powers kVA Elements
Show Losses

Export Voltages
Export Currents
Export Powers
Export Losses
Export Meters

Esse modelo pode ser adaptado de acordo com o objetivo da simulação.

Boas Práticas​

Para garantir organização e reprodutibilidade, recomenda-se:

  • utilizar um arquivo principal;
  • separar elementos por função;
  • utilizar caminhos relativos;
  • manter nomes padronizados;
  • documentar todos os arquivos;
  • registrar a origem dos dados;
  • separar entradas e resultados;
  • utilizar controle de versão;
  • criar cenários específicos;
  • testar o modelo progressivamente;
  • registrar a versão do OpenDSS;
  • evitar arquivos duplicados;
  • criar cópias de segurança;
  • manter um arquivo de instruções;
  • validar o modelo após alterações;
  • preservar os resultados de referência.

Projeto_NE PSEL/

Redirect Modelo/Circuito.dss

A adoção dessa estrutura facilita a integração entre pesquisadores e a continuidade dos projetos.

Considerações Técnicas​

A estruturação adequada dos arquivos não altera diretamente os cálculos realizados pelo OpenDSS, mas influencia significativamente a confiabilidade e a manutenção do modelo.

Projetos organizados permitem:

  • localizar erros com maior rapidez;
  • compreender as dependências entre os elementos;
  • reutilizar componentes;
  • comparar cenários;
  • automatizar simulações;
  • compartilhar os modelos;
  • registrar alterações;
  • reproduzir os resultados.

O arquivo Master.dss deve concentrar o controle da simulação, enquanto os demais arquivos devem reunir os elementos conforme sua função.

A separação entre modelo, dados, cenários, scripts, resultados e documentação é fundamental para garantir a rastreabilidade dos estudos e a continuidade das atividades desenvolvidas no OpenDSS.
